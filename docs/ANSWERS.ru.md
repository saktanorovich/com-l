## 1. Протокол итератора  (`01_iterator_protocol`)

**В: Чем отличается итерируемый объект (iterable) от итератора (iterator)?**
У *iterable* есть `__iter__()`, возвращающий итератор (list, str, dict, file). У *iterator* есть `__next__()` (возвращает следующий элемент или бросает `StopIteration`) и `__iter__()`, возвращающий сам объект. Итераторы одноразовые; iterable можно обходить повторно.

**В: Что делает `for x in obj`?**
Вызывает `iter(obj)`, затем многократно `next(it)` до `StopIteration` (см. `manual_for_loop`).

**В: Генератор или класс-итератор?**
Функция-генератор (с `yield`) автоматически создаёт итератор; состояние хранится в приостановленном фрейме. Ленивый, O(1) памяти, гораздо короче класса. Класс нужен, когда требуются дополнительные методы/состояние (например, `peek`, `reset`).

**В: Чем опасен возврат `self` из `__iter__`?**
Второй цикл по тому же объекту окажется пустым (итератор исчерпан). Для многоразовых коллекций возвращайте в `__iter__` новый итератор (`CountdownIterable`).

**В: `iter(callable, sentinel)`?** Вызывает callable, пока тот не вернёт sentinel, например `iter(lambda: f.read(1024), "")`.

Также: `yield from`, `itertools` (`islice`, `chain`, `tee`), генераторы нельзя перемотать, `StopIteration` внутри генератора превращается в `RuntimeError` (PEP 479).

## 2. Декораторы  (`02_decorators`)

**В: Что такое декоратор?**
Вызываемый объект, принимающий функцию и возвращающий замену; `@d def f` - это `f = d(f)`. Применяется для сквозной функциональности: логирование, замер времени, повторы, кэширование, авторизация.

**В: Зачем `functools.wraps`?**
Без него обёртка скрывает `__name__`, `__doc__`, аннотации, `__wrapped__` - это ломает отладку, интроспекцию и документацию.

**В: Как работают декораторы с аргументами?**
Три уровня: `retry(3)` возвращает настоящий декоратор, который возвращает обёртку (`retry` в `main.py`).

**В: Порядок вложенных декораторов?**
Применяются снизу вверх (`@a @b def f` = `a(b(f))`); при вызове первой срабатывает внешняя обёртка.

**В: Декораторы-классы?** Реализуют `__call__`; удобны для состояния. Для методов нужен `__get__`, либо используйте функциональные декораторы.

**В: Подводные камни?** Забытый `return`, непереданные `*args, **kwargs`, изменяемое общее состояние в кэше (неограниченный рост - лучше `functools.lru_cache(maxsize=...)`), нехэшируемые аргументы при мемоизации.

## 3. Потоки и GIL  (`03_threading_gil`)

**В: Что такое GIL?**
Мьютекс в CPython, из-за которого байт-код Python в каждый момент выполняет только один поток. Он защищает внутренности интерпретатора (счётчики ссылок, управление памятью).

**В: Каковы последствия?**
- CPU-bound код не ускоряется на потоках -> используйте `multiprocessing` / `ProcessPoolExecutor`, NumPy/C-расширения, освобождающие GIL, или другие рантаймы.
- I/O-bound код (сеть, диск, `sleep`) выигрывает: GIL освобождается при блокировке -> `ThreadPoolExecutor` или `asyncio` для множества соединений.

**В: Делает ли GIL мой код потокобезопасным?**
Нет. `counter += 1` - это загрузка/сложение/сохранение; интерпретатор может переключить поток между ними (потерянные обновления). Используйте `threading.Lock`, `queue.Queue` или избегайте общего состояния. Составные операции по умолчанию небезопасны.

**В: Потоки, процессы или asyncio?**
Потоки: общая память, дёшево, I/O-bound. Процессы: отдельная память и свой GIL у каждого, CPU-bound, платим за pickle/IPC. asyncio: один поток, кооперативная многозадачность, лучше всего для тысяч ожиданий I/O; блокирующие вызовы стопорят цикл событий.

**В: Другие инструменты?** `RLock` (реентерабельный), `Semaphore`, `Event`, `Condition`, взаимные блокировки (единый порядок захвата, таймауты), daemon-потоки, `join()`.

**В: Что нового?** В Python 3.13+ есть *экспериментальная free-threaded* сборка (PEP 703, без GIL) - не по умолчанию; поддержка в библиотеках ещё развивается. Для банка в enterprise-среде исходите из того, что GIL есть.

Для LLM-нагрузок: вызовы API - I/O-bound -> потоки/asyncio с ограничением частоты и повторами; постобработка/числодробилки -> процессы.

## 4. Списковые включения  (`04_list_comprehension`)

**В: Синтаксис?** `[expr for x in it if cond]`; словарь `{k: v for ...}`, множество `{e for ...}`, генератор `(e for ...)`.

**В: Зачем их использовать?** Читаемее и обычно быстрее циклов с `append` (нет повторного поиска метода, оптимизированный байт-код).

**В: Порядок во вложенных включениях?** Тот же, что у вложенных циклов, записанных слева направо: `[x for sub in nested for x in sub]`.

**В: Списковое включение или генераторное выражение?** Список строится целиком в памяти; генератор ленивый, O(1) памяти и одноразовый. Для `sum`, `any`, `max` и т. п. используйте генератор.

**В: Область видимости?** В Python 3 переменная цикла не «утекает». Но замыкания захватывают переменные, а не значения: `[lambda: i for i in range(3)]` вернут 2 для всех -> исправление: `lambda i=i: i`.

**В: Когда НЕ использовать?** Побочные эффекты, глубокая вложенность, несколько условий, ухудшающих читаемость, слишком длинные выражения - используйте обычный цикл.

**В: Условное выражение или фильтр?** `[a if c else b for x in it]` (преобразование) против `[x for x in it if c]` (фильтр) - важно положение `if`.

## 5. Работа с файлами и управление ресурсами  (`05_file_handling`)

**В: Зачем `with open(...)`?**
Гарантирует `close()` (сброс буфера + освобождение дескриптора) даже при исключениях. Если полагаться на GC или ручной `close()`, дескрипторы утекают, а буферизованные данные могут потеряться.

**В: Как работают менеджеры контекста?**
`__enter__` захватывает и возвращает ресурс; `__exit__(exc_type, exc, tb)` освобождает; вернуть истинное значение - подавить исключение. Либо `@contextlib.contextmanager` с `try/finally` вокруг `yield`. `ExitStack` - для динамического числа ресурсов.

**В: Как читать большие файлы?**
Итерироваться по файловому объекту (построчно) или `read(size)` блоками; никогда не делать `read()`/`readlines()` для многогигабайтного файла.

**В: Текстовый и бинарный режим, кодировка?**
Всегда явно указывайте `encoding="utf-8"` для текста (по умолчанию зависит от локали); для байтов - `"rb"/"wb"`. В текстовом режиме переводы строк преобразуются (`newline`).

**В: Как безопасно записать файл?**
Записать временный файл в том же каталоге, `flush` + `os.fsync` (если важна долговечность), затем `os.replace` (атомарно) - читатели никогда не увидят наполовину записанный файл (`atomic_write`).

**В: Другое:** `pathlib.Path` вместо строковых путей, `tempfile`, `shutil`, режимы `r/w/a/x/+`, обработка `FileNotFoundError`/`PermissionError`, блокировка файлов при конкурентной записи, буферизация и `flush` в `open`.

## 6. Наследование классов  (`06_class_inheritance`)

**В: Как работает `super()`?**
Возвращает прокси, делегирующий **следующему классу в MRO**, а не обязательно непосредственному родителю. Кооперативное множественное наследование требует, чтобы каждый класс вызывал `super()`.

**В: Что такое MRO?**
Порядок разрешения методов (Method Resolution Order), вычисляется линеаризацией C3; смотрится через `Cls.__mro__`. Ромб `D(B, C)` -> `D, B, C, A, object`; `A` вызывается один раз.

**В: Абстрактные классы?**
`abc.ABC` + `@abstractmethod`: подкласс нельзя инстанцировать, пока не переопределены все абстрактные методы.

**В: Наследование или композиция?**
Композиция («has-a») предпочтительна ради гибкости; наследование («is-a») - для настоящего подтипирования (принцип Лисков). Миксины добавляют небольшое переиспользуемое поведение (`JsonMixin`).

**В: Атрибуты класса и экземпляра?**
Атрибуты класса общие для всех экземпляров (ловушка, если это списки/словари); `self.x = ...` создаёт атрибут экземпляра, затеняющий атрибут класса.

**В: Другое:** `isinstance`/`issubclass`, переопределение и расширение (вызов `super().method()`), `__init_subclass__` для реестров/плагинов, искажение имён (`__x`), `@classmethod` / `@staticmethod`, `@property`, утиная типизация / `Protocol`, `dataclass`.

## 7. Изменение списков (поверхностное копирование)  (`07_list_mutation`)

**В: `b = a`, `a.copy()` или `deepcopy`?**
`b = a` - тот же объект (алиас). `a.copy()`, `a[:]`, `list(a)`, `copy.copy(a)` - новый внешний список, но **те же внутренние объекты** (поверхностная копия). `copy.deepcopy(a)` - рекурсивно копирует всё.

**В: Классический пример?**
`a = [[1], [2]]; b = a.copy(); b[0].append(9)` -> `a` тоже становится `[[1, 9], [2]]`.

**В: Ошибка `[[0]*3]*3`?**
Создаёт 3 ссылки на одну строку; изменение одной ячейки меняет все строки. Используйте `[[0]*3 for _ in range(3)]`.

**В: Изменяемые аргументы по умолчанию?**
`def f(x, lst=[])` - значение по умолчанию создаётся один раз при определении функции и разделяется между вызовами. Используйте сентинел `None`.

**В: Изменение списка во время итерации?**
Удаление сдвигает индексы и пропускает элементы. Стройте новый список (включением), итерируйтесь по копии или делайте `nums[:] = [...]` для изменения на месте с сохранением идентичности (важно, если у других есть ссылка).

**В: `+=` или `+`?**
`a += [x]` изменяет на месте (`extend`) и затрагивает алиасы; `a = a + [x]` создаёт новый список.

**В: `sort()` или `sorted()`?** `sort()` сортирует на месте и возвращает `None`; `sorted()` возвращает новый список. Классическая ошибка: `x = x.sort()`.

**В: Неизменяемый кортеж со списком внутри?** Сам кортеж изменить нельзя, но внутренний список можно (`t[0].append(1)`) - а `t[0] += [1]` бросает `TypeError` *уже после* изменения.

**В: Аргументы функции?** Python передаёт ссылки на объекты: изменение списка-аргумента внутри функции видно вызывающему коду; переприсваивание параметра - нет.
